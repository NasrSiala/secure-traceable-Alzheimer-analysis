### AUD-002 — `app_worker` can read credential tables

- **Severity:** Medium
- **Category:** Security
- **Location:** `docs/specs/schema.sql:258`
- **Description:** `GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_api, app_worker` gives the worker read access to `users` (Argon2id hashes, e-mails), `refresh_tokens` (token hashes) and `login_attempts` (e-mails, IPs).
- **Evidence:** On PostgreSQL 16, `SET ROLE app_worker; SELECT password_hash FROM users;` returns `$argon2id$x`; `refresh_tokens` and `login_attempts` also readable. Architecture §8 gives these tables to SVC-identity, read only by SVC-api.
- **Root cause:** one blanket SELECT grant for both roles; the worker's real read set (cases, jobs, artifacts, files, logs, models, configs) was never separated from the account tables.
- **Impact:** the worker is the process that parses untrusted uploads (WFDB/CSV) and loads model weights. If it is compromised, the attacker also gets every password hash and login metadata, defeating the "défense en profondeur" purpose of ADR-15.
- **Recommended fix:** `REVOKE SELECT ON users, refresh_tokens, login_attempts FROM app_worker;` Validated with `audit/proposals/schema-least-privilege.diff` + `audit/tools/verify_schema_patch.sh` (original: 6 failed checks; patched: 23/23 pass, including claim-job, artifact insert/anchor, register_model, case purge cascade).
- **Status:** Fixed
- **Fix applied:** `docs/specs/schema.sql` grants section (applied with your approval, suite v2.1.2, Backend Schema v2.0.3, CHANGELOG entry); tables/columns/constraints untouched. Verified: `audit/tools/verify_schema_patch.sh docs/specs/schema.sql` → 23/23 pass on PostgreSQL 16 (was 6 failures).

### AUD-003 — TRD says `registry.py` runs as `app_worker`; only `app_api` may write `validation_configs`

- **Severity:** Medium
- **Category:** Data (contract between TRD and schema)
- **Location:** `docs/specs/02-trd.md:118` vs `docs/specs/schema.sql:262`
- **Description:** TRD §8.1: "`scripts/registry.py` s'exécute … avec les droits admin de la base (`app_worker`)". schema.sql grants `INSERT, UPDATE ON validation_configs` to `app_api` only.
- **Evidence:** PostgreSQL 16: `SET ROLE app_worker; INSERT INTO validation_configs …` → `ERROR: permission denied for table validation_configs`; same statement as `app_api` → `INSERT 0 1`.
- **Root cause:** the TRD names the role used by `register_model.py` (which does need `app_worker`: INSERT on `models`), not the role `registry.py` needs. Schema + `schema.sql` own authorisations (AGENTS.md ownership table).
- **Impact:** an implementer following the TRD gets `permission denied` on `registry.py config new|activate` (T4.7), or widens `app_worker` grants against ADR-15.
- **Recommended fix:** TRD §8.1 → `registry.py` runs with the `app_api` role (it covers config INSERT/UPDATE `is_active` and `models.is_active`); `register_model.py` runs with `app_worker`. No schema change.
- **Status:** Fixed
- **Fix applied:** `docs/specs/02-trd.md` §8.1 (TRD v2.0.3); verified by `audit/tools/verify_schema_patch.sh` (config INSERT/UPDATE `is_active` OK as `app_api`, denied as `app_worker`).

### AUD-004 — Fabric test network publishes CA, orderer and peer ports on all host interfaces

- **Severity:** Low
- **Category:** Security
- **Location:** `fabric/compose/compose.yaml:45-46, 71-72, 97-98, 142-144, 184-185, 225-226`
- **Description:** `ports: - "18054:7054"` etc. bind 0.0.0.0. On a shared network (lab Wi-Fi, defence room) the three Fabric CAs, the orderer (incl. admin port 7053) and both peers are reachable by anyone.
- **Evidence:** every `ports:` entry lacks a host IP; `network.sh check_ports` probes only `127.0.0.1`.
- **Root cause:** Compose default bind address; the ports exist only for host-side tooling, which needs loopback.
- **Impact:** limited by TLS/mTLS and random 128-bit bootstrap passwords, but an unnecessary identity-issuing surface during a demo on an untrusted network.
- **Recommended fix:** prefix every published port with `127.0.0.1:`; add a static regression test.
- **Status:** Fixed
- **Fix applied:** `fabric/compose/compose.yaml` (7 ports → `127.0.0.1:`); tests `test_published_ports_are_bound_to_loopback`, `test_host_ports_in_script_match_compose`; live `docker port` shows `127.0.0.1:18050-18056`.

### AUD-005 — CA bootstrap/enrolment secrets written with default file permissions

- **Severity:** Low
- **Category:** Security
- **Location:** `fabric/network.sh:111-136` (`write_secrets`)
- **Description:** `fabric/.runtime/ca.env` (all CA bootstrap and enrolment passwords) is created by `Path.write_text` with the default umask (typically 0644), so other local users can read it on a shared Linux machine.
- **Evidence:** code inspection; on Windows the bits are not enforced so the symptom is Linux/macOS-only (could not run there).
- **Root cause:** no restrictive mode set.
- **Impact:** local credential disclosure for the lifetime of the test network.
- **Recommended fix:** create the file under `umask 077` and `chmod 600`; add a POSIX-only regression test.
- **Status:** Fixed
- **Fix applied:** `fabric/network.sh` `write_secrets` (`umask 077`, `chmod 600`, LF writer); tests `test_write_secrets_produces_a_clean_lf_env_file` (passes) and `test_write_secrets_is_owner_only` (POSIX only — skipped on this Windows host).

### AUD-006 — `network.sh status` is not read-only: it creates host directories and a Docker network, and takes ~10 s, on a stopped network

- **Severity:** Low
- **Category:** Correctness
- **Location:** `fabric/network.sh:214-217` (`cmd_status`), called first thing by `cmd_start` (`:351`)
- **Description:** `status` always runs `docker compose run tools osnadmin …` to ask the orderer which channels it has, even when the orderer container does not exist.
- **Evidence:** after `stop`, `bash fabric/network.sh status` took 10.0 s, left `fabric/organizations/`, `fabric/channel-artifacts/` and the Docker network `saam-medtrace` behind (verified with `ls` / `docker network ls`; removed again by `stop`).

- **Impact:** a status probe mutates state (network + root-owned host directories on Linux) and could pull the tools image just to report "unhealthy". Latency is unchanged by the fix (≈ 9–10 s before and after, dominated by Docker CLI round-trips).
- **Recommended fix:** query the orderer only when `saam-medtrace-orderer` is running; add a fabric-marked regression test that `status` on a stopped network leaves no directory or network behind.
- **Status:** Fixed
- **Fix applied:** `fabric/network.sh` `cmd_status` (orderer query only if the orderer runs); new fabric test `test_status_on_a_stopped_network_changes_nothing` passes; manual check: `ls fabric` and `docker network ls` clean after `status`.

### AUD-007 — `network.sh` depends on a bare `python`, mis-reports its absence, and duplicates the port list

- **Severity:** Low
- **Category:** Config
- **Location:** `fabric/network.sh:22` (unused `HOST_PORTS`), `:87-108` (`check_ports`), `:111-136` (`write_secrets`)

### AUD-008 — Column-level UPDATE rights are broader than the documented immutability rules

- **Severity:** Low
- **Category:** Security / Data
- **Location:** `docs/specs/schema.sql:262` (`validation_configs`), `:272` (`artifacts`) vs `docs/specs/04-backend-schema.md:123, 257`
- **Description:** Schema §5.1 says threshold rows "ne sont jamais modifiées" and §10 says `artifacts.sha256`, `type`, `parent_artifact_id` are never updated after insert (only `anchor_*`, `tx_id`, `anchored_at`). The grants allow whole-row UPDATE.
- **Evidence:** PostgreSQL 16: `SET ROLE app_worker; UPDATE artifacts SET sha256 = repeat('f',64)` → `UPDATE 1`; `SET ROLE app_api; UPDATE validation_configs SET conf_high = 0.01` → `UPDATE 1`.
- **Root cause:** table-level grants where column-level ones were intended (as already done for `models.is_active`).
- **Impact:** the displayed hash copy can be rewritten (verification reads Fabric, so integrity detection is unaffected) and past validation thresholds can be altered, weakening NFR-07 reproducibility.
- **Recommended fix:** `GRANT UPDATE (is_active)` on `validation_configs`; `GRANT UPDATE (anchor_status, anchor_attempts, tx_id, anchored_at)` on `artifacts` (in the same validated patch as AUD-002).
- **Status:** Fixed
- **Fix applied:** `docs/specs/schema.sql` grants section (applied with your approval, suite v2.1.2, Backend Schema v2.0.3, CHANGELOG entry); tables/columns/constraints untouched. Verified: `audit/tools/verify_schema_patch.sh docs/specs/schema.sql` → 23/23 pass on PostgreSQL 16 (was 6 failures).

### AUD-009 — The 30-day `login_attempts` purge required by Schema §16 is impossible for `app_api`

- **Severity:** Low
- **Category:** Data
- **Location:** `docs/specs/schema.sql:264` vs `docs/specs/04-backend-schema.md:326`
- **Description:** Schema §16 retains `login_attempts` 30 days, purged "tâche au démarrage de l'API"; `app_api` only has INSERT.
